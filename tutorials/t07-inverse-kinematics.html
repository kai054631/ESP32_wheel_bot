Tutorial 7 of 8 — Drive-first track

drive(v, ω): Inverse Kinematics

Turn a single command — go this fast, turn this hard — into the two independent wheel speeds that produce it.
⏱ 75–90 min
🎯 Goal: forward, reverse, pivot, and arc on command
📍 builds on motorMove()

What you're building

Right now you can command each wheel individually with motorMove(mot, value). What you actually want to command is the robot: "drive forward at this speed" or "turn on the spot at this rate." drive(v, ω) is the function that translates between those two — a robot-level command in, two wheel-level motorMove calls out.

drive(v, ω)  ──►  v_left, v_right  ──►  motorMove(A, ...) + motorMove(B, ...)

Concepts, explained inline

The two numbers that describe any 2D robot motion

SymbolMeaningUnits
vforward/backward speed of the robot's centrem/s
ωrotation rate; positive = counter-clockwiserad/s

v = 0.2, ω = 0 is "drive straight at 0.2 m/s." v = 0, ω = 1 is "spin in place." Anything in between is an arc. This (v, ω) pair is the standard way robotics describes 2D motion — it's what you'd publish on a ROS /cmd_vel topic, for instance.

Deriving the wheel speeds

Picture the robot rotating about some point on the line through both wheels — the "instantaneous centre of rotation." If the two wheels are a track width b apart and the robot's centre is moving at v while rotating at ω, the inside wheel must travel slower than the centre and the outside wheel faster, by an amount proportional to how far each is from the centre — b/2:

       ω  (turning left = positive)
       ↺
  ┌────┼────┐
  │    │    │
 L●----●----●R      track width b
  └────┴────┘
       v  (centre speed)

  v_left  = v − ω·(b/2)
  v_right = v + ω·(b/2)

Check it against intuition: pivoting in place is v = 0, so v_left = −ω·b/2 and v_right = +ω·b/2 — equal and opposite, which is exactly a spin-in-place. Driving straight is ω = 0, giving v_left = v_right = v, as it should.

Measure your track width

b isn't a nominal chassis spec — measure the actual centre-to-centre distance between your two wheels' contact points on the ground.

This mapping is open-loop — say why that matters

You don't have closed-loop speed control yet (that's T8). So "wheel speed" here really means "a duty proportional to speed," not a guaranteed physical speed — two motors driven at the same duty will not turn at exactly the same real speed, because no two small DC motors are identical. That's fine for this tutorial; the goal is correct direction and shape of motion (forward, pivot, arc), not perfect straight-line tracking. You'll measure exactly how far off straight it drifts, and that number becomes T8's reason to exist.

Saturation: clip both wheels together, or ruin the turn

This is a real task, not a footnote. Suppose max wheel speed is 1.0 and your kinematics computes v_left = 0.6, v_right = 1.3. Clamping only v_right down to 1.0 seems harmless — but it silently changes the difference between the two wheel speeds, which is what encodes ω. The robot now turns less sharply than commanded, with no warning. The correct fix: if either wheel exceeds the limit, scale both wheel speeds down by the same factor, so their ratio — and therefore the turn radius — is preserved.

Your hardware

No new pins — this layers on top of motorMove(mot, value) from your existing driver code, which already takes a signed ±100 value per motor.

Code skeleton

#define TRACK_WIDTH_M   1   // measured, metres
#define MAX_WHEEL_MPS   2   // measured or estimated top speed

void drive(float v, float omega)
{
    float v_left  = 3;
    float v_right = 4;

    float max_mag = 5;   // largest |wheel speed| of the two
    if (max_mag > MAX_WHEEL_MPS) {
        float scale = 6;
        v_left  *= scale;
        v_right *= scale;
    }

    int duty_left  = 7;   // v_left  → motorMove's ±100 range
    int duty_right = 7;   // v_right → motorMove's ±100 range

    motorMove(MOTOR_A, duty_left);
    motorMove(MOTOR_B, duty_right);
}

Checkpoints

You're done when: drive(0.2, 0) drives straight forward, drive(-0.2, 0) straight back, drive(0, 1.0) pivots in place without net translation, and a nonzero v with nonzero ω traces a visible arc. Then: mark a start line, run drive(v, 0) for a measured 2 m of travel, and record how far off a straight line the robot ends up — write this number down, it's T8's baseline to beat.

Common failure modes

  • Robot pivots the wrong way for positive ω. Sign convention mismatch between your formula and which motor is "left" — recheck against the diagram, and against motorMove's own forward/backward polarity per motor.
  • Straight drive() curves noticeably even with ω = 0. Expected to some degree — this is exactly the drift T8 will fix. Large curving (much more than the two wheels' natural mismatch) suggests a units or scaling bug instead — check duty conversion.
  • Pivot has visible net translation. v_left and v_right aren't coming out as exact opposites — check the track-width term is applied identically to both, just with opposite sign.
  • Large ω silently produces a gentler turn than expected. This is the un-clipped saturation bug — check both wheels are scaled together, not clamped independently.
Answer key — open only after you've attempted it 
float v_left  = v - omega * (TRACK_WIDTH_M / 2.0f);
float v_right = v + omega * (TRACK_WIDTH_M / 2.0f);

float max_mag = fmaxf(fabsf(v_left), fabsf(v_right));
if (max_mag > MAX_WHEEL_MPS) {
    float scale = MAX_WHEEL_MPS / max_mag;
    v_left  *= scale;
    v_right *= scale;
}

int duty_left  = (int)((v_left  / MAX_WHEEL_MPS) * 100.0f);
int duty_right = (int)((v_right / MAX_WHEEL_MPS) * 100.0f);

Note duty_left/duty_right can still exceed ±100 by a rounding hair after the scale step — motorMove's own clamp (from the earlier fixes) is the safety net here, not a substitute for doing the scaling correctly.
