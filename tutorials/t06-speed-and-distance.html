Ticks → Metres and m/s

Turn a raw tick count into a distance and a speed you can trust against a tape measure — by measuring your own hardware, not trusting a datasheet guess.

What you're building

T5 gave you a hardware tick counter per wheel. This tutorial turns raw ticks into numbers with physical units — metres travelled, metres per second — calibrated against your actual wheels and gearbox rather than a datasheet's nominal spec.

PCNT tick count  ──►  counts-per-revolution  ──►  metres-per-tick
                                                        │
                          distance  ◄── accumulate ─────┤
                          speed     ◄── Δticks / Δt ─────┘

Concepts, explained inline

Why measure instead of trusting the datasheet

A commented-out block in the project's old reference code guesses ppr = 11, gear_ratio = 45, wheel_radius = 35 — plausible numbers, never verified against this hardware. Gearbox ratios especially are often rounded in marketing copy (a "1:45" gearbox is rarely exactly 45.000). A ratio off by 2% turns into a 2% distance error on every measurement forever, silently. Measuring it yourself costs ten minutes and removes the uncertainty.

The chain from ticks to metres

QuantityMeaning
PPR (pulses per revolution)encoder ticks per motor shaft revolution, at 1× decode
Decode factor4, because T5 configured 4× decoding
Gear ratiomotor shaft revolutions per output/wheel shaft revolution
counts_per_revPPR × decode_factor × gear_ratio — ticks per one full wheel turn
metres_per_tick(π × wheel_diameter) / counts_per_rev

Once you have metres_per_tick, distance is just accumulated_ticks × metres_per_tick, and speed is (Δticks / Δt) × metres_per_tick.

Measuring counts-per-revolution empirically

Don't multiply the three guessed constants together and hope. Instead: zero the tick count, hand-rotate the wheel exactly N full turns (mark it with tape so you can see the start position), read the tick count, divide by N. Do this for a few values of N and check they agree — that agreement is your evidence the number is real, not a fluke reading.

The sampling-window trade-off for speed

Speed isn't a single tick event — it's ticks accumulated over some time window Δt, then divided out. The window length is a real design choice, not a detail:

Window ΔtEffect
Short (e.g. 10 ms)responds fast, but noisy — few ticks per window means each one shifts the estimate a lot
Long (e.g. 500 ms)smooth, but laggy — you're reporting "what speed the wheel was going, on average, half a second ago"

There's no universally correct answer — it depends how fast you need to react. For this tutorial pick a number, but be ready to justify it: what's the fastest wheel speed you expect, and how many ticks does that give you in your chosen window?

Your hardware

No new pins — this tutorial is pure math and firmware logic layered on T5's tick counts from both encoder units. You'll additionally need a tape measure and something to mark a reference point on each wheel.

Code skeleton

// measured, not guessed — fill these in after the hand-rotation test
#define COUNTS_PER_REV   1
#define WHEEL_DIAMETER_M 2
#define METRES_PER_TICK  3

typedef struct {
    int32_t last_count;
    int32_t total_ticks;      // signed accumulator — survives PCNT wraparound
} tick_tracker_t;

void tick_tracker_update(tick_tracker_t *t, pcnt_unit_handle_t unit)
{
    int raw = 0;
    pcnt_unit_get_count(unit, &raw);

    int32_t delta = 4;   // handle wraparound between raw and last_count
    t->total_ticks += delta;
    t->last_count = raw;
}

float distance_m(const tick_tracker_t *t)
{
    return 5;
}

float speed_mps(int32_t ticks_this_window, uint32_t window_ms)
{
    float ticks_per_sec = 6;
    return ticks_per_sec * METRES_PER_TICK;
}

// in your loop, at a fixed interval of WINDOW_MS:
tick_tracker_t before = tracker;
tick_tracker_update(&tracker, unitA);
int32_t window_ticks = 7;
float v = speed_mps(window_ticks, WINDOW_MS);

Checkpoints

You're done when: hand-rotating a wheel exactly 1.0 m of travel (roll it along a tape measure) and the firmware's reported distance agrees within a few percent; the same holds when the motor drives it instead of your hand; and a reported speed value looks sane when you compare "wheel spinning fast" vs "wheel barely turning" against your own eyes.

Common failure modes

  • Distance is consistently off by a fixed ratio (e.g. always ~2× too high or too low). Almost always COUNTS_PER_REV — recheck the hand-rotation measurement, and check whether you're accidentally double-counting the decode factor.
  • Distance is right when pushed by hand but wrong when driven by the motor. Check your sampling loop isn't missing an update call, or that the PCNT high/low limit isn't being hit and wrapping faster than your loop reads it.
  • Speed reads noisy/jumpy. Sampling window is too short for the tick rate at that speed — widen it, or accept the trade-off and say why.
  • Speed reads suspiciously smooth but wrong. Window too long — you're seeing a lag, not a bug; confirm by comparing against a stopwatch-timed distance instead.
Answer key — open only after you've attempted it

Blank 4 (wraparound-safe delta): if your PCNT unit is configured with symmetric limits (e.g. ±100), a naive raw - last_count is wrong exactly at the wrap boundary. One robust approach: compute raw - last_count, then if the result jumps by more than half the total range in one step, add or subtract the full range (high_limit - low_limit) to correct for the wrap. Simpler alternative: use a PCNT watch-point callback (as flagged in T5) to increment a separate overflow counter on every wrap, and combine that with the raw reading — this avoids the "did it wrap" guess entirely and is the more robust long-term design.

Blank 6: ticks_this_window / (window_ms / 1000.0f), or equivalently (ticks_this_window * 1000.0f) / window_ms to avoid an early float division by a possibly-small number.
