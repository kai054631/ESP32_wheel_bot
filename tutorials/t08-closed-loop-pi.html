Closed-Loop PI Speed Control

Make each wheel actually hit the speed it's told to, by measuring and correcting — the step that turns an approximate robot into an accurate one.
⏱ 90 min
🎯 Goal: straight-line drive better than T7's baseline; a 1 m square that returns near start

What you're building

T7's drive(v, ω) is open-loop: it commands a duty and hopes the motor obeys. It doesn't, exactly — you measured that drift over 2 m. This tutorial closes the loop: measure each wheel's actual speed (from T6), compare it to what was commanded, and continuously correct the duty until they match.

Concepts, explained inline

Why open-loop can't be fixed by "better" constants

Two DC motors of the same model are never identical — small differences in windings, bearings, and gearbox friction mean the same duty produces measurably different speeds. No amount of tuning a single global duty-to-speed formula fixes this, because the error is different for each motor. The only way out is to look at what each wheel is actually doing, right now, and correct it — which is what a control loop is.

P and I, in plain terms

TermResponds toEffect
Proportionalcurrent error (target − measured)bigger error → bigger correction, immediately
Integralaccumulated error over timekills the small steady-state error P alone leaves behind

Why P alone isn't enough: with only P, a small residual error produces only a small correction — and if that correction is smaller than what's needed to overcome friction, the wheel settles slightly slow forever. The integral term keeps growing for as long as any error persists, eventually forcing it to zero.

error = target_speed - measured_speed
integral += error * dt
output = Kp * error + Ki * integral

Two failure modes every naive PI hits — cover both, or it will misbehave

Integral windup: if the wheel is physically stalled (or the target is unreachable), error stays large and integral grows without bound. When the obstruction clears, that huge accumulated integral fires a massive overcorrection — the wheel lurches. Fix: clamp integral to a sane range, or freeze it while the output is already saturated.
Output clamping: the computed output must be clamped to ±DUTY_MAX before it reaches motorMove — the same unchecked-range issue you already found in ledc_set_duty applies here one layer up. An unclamped PI output can compute values wildly outside what the motor driver can accept.

Why the control loop needs a faster FreeRTOS tick

You already found CONFIG_FREERTOS_HZ = 100, meaning a 10 ms tick — the motor ramp problem from T3. The same limit applies here, harder: a PI loop's dt needs to be short and consistent for the integral term's math to behave predictably. Raise it via idf.py menuconfig → Component config → FreeRTOS → Kernel → configTICK_RATE_HZ → 1000, then rebuild. This is a one-time sdkconfig change, not a source edit.

vTaskDelayUntil, not vTaskDelay

vTaskDelay(x) waits x ticks from when it's called — so if your loop body takes variable time to run, the interval between iterations drifts. vTaskDelayUntil instead targets a fixed wake-up time regardless of how long the body took, which keeps dt constant — exactly what the PI math above assumes.

Tuning procedure

Standard order, don't skip steps: set Ki = 0, raise Kp from zero until the wheel responds promptly without visibly oscillating around the target. Then add a small Ki and watch the steady-state error shrink to zero over a second or two. If it oscillates once Ki is added, it's too large — reduce it.

Your hardware

No new pins. This is the first tutorial that runs T5's encoders, T6's speed conversion, and T7's drive() together in one continuously-running task.

Code skeleton

typedef struct {
    float kp, ki;
    float integral;
    float output_min, output_max;
} pi_controller_t;

float pi_update(pi_controller_t *c, float target, float measured, float dt)
{
    float error = 1;

    // only accumulate integral if we're not already saturated —
    // this is the anti-windup guard
    float unclamped_output = c->kp * error + c->ki * (c->integral + error * dt);
    if (unclamped_output >= c->output_min && unclamped_output <= c->output_max) {
        c->integral += 2;
    }

    float output = c->kp * error + c->ki * c->integral;
    if (output > c->output_max) output = 3;
    if (output < c->output_min) output = 3;
    return output;
}

void motor_control_task(void *arg)
{
    pi_controller_t pid_A = { .kp = 4, .ki = 4,
                               .output_min = -100, .output_max = 100 };

    TickType_t last_wake = xTaskGetTickCount();
    const TickType_t period = 5;   // ticks, at your new 1000 Hz rate

    while (1) {
        float measured = 6;   // from T6's speed_mps(), motor A
        float duty = pi_update(&pid_A, target_speed_A, measured, 7);
        motorMove(MOTOR_A, (int)duty);

        8;   // sleep until exactly one period from last_wake
    }
}

Checkpoints

You're done when: commanding straight-line drive at a fixed v holds a visibly straighter line over 2 m than T7's baseline number; pressing a light hand-load against one wheel while driving causes it to briefly slow then recover to target speed rather than staying slow; and the robot completes a commanded 1 m square (four 1 m sides, four 90° turns) and ends up close to its starting point and heading.

Common failure modes

  • Wheel oscillates / buzzes at a fixed speed target. Kp too high — reduce it and re-test before touching Ki.
  • Reaches target but overshoots then settles. Ki too high relative to Kp — reduce Ki.
  • Wheel violently lurches after being blocked and released. Classic integral windup — check the anti-windup guard is actually preventing accumulation while saturated, not just clamping the final output.
  • Loop behaves differently depending on system load (other tasks running). You're using vTaskDelay instead of vTaskDelayUntil, or the FreeRTOS tick rate wasn't actually raised — check sdkconfig.
  • Speed measurement is zero or stale inside the control loop. Check the tick tracker update call is happening every loop iteration, not just once at startup.
