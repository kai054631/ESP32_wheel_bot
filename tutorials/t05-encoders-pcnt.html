Encoders with PCNT

Turn the quadrature signal from each wheel's encoder into a hardware-counted tick total, with the correct sign for direction.
⏱ 75–90 min
🎯 Goal: ticks that increase forward, decrease backward, and repeat on hand-turns
📍 GPIO 8, 3, 46, 9

What you're building

Each wheel's encoder outputs two square waves, A and B, one edge per small rotation of the shaft. Right now those edges go nowhere. By the end of this tutorial, the ESP32-S3's PCNT (pulse counter) hardware peripheral will be watching both signals for each wheel and holding a running tick total you can read at any time — no CPU cycles spent polling, no missed edges even at speed.

encoder A/B (motor A)  ──►  PCNT unit 0  ──►  int16 tick count
encoder A/B (motor B)  ──►  PCNT unit 1  ──►  int16 tick count

Concepts, explained inline

Quadrature: two signals, one direction

A single encoder channel only tells you that the shaft turned, not which way. Quadrature encoders fix this with a second channel, B, whose square wave is shifted 90° from A. Which one leads the other tells you direction:

Forward (A leads B):        Backward (B leads A):

A  ┐   ┌───┐   ┌───┐        A    ┐   ┌───┐   ┌───┐
   └───┘   └───┘   └──           └───┘   └───┘   └──
B    ┐   ┌───┐   ┌───┐      B  ┐   ┌───┐   ┌───┐
     └───┘   └───┘   └           └───┘   └───┘   └──

Read as a 2-bit state (A,B), one full electrical cycle steps through 4 states in a fixed order — forward and backward walk that order in opposite directions:

DirectionState sequence (A,B)
Forward00 → 10 → 11 → 01 → 00 …
Backward00 → 01 → 11 → 10 → 00 …

Counting every edge on both channels (4 transitions per full cycle) is called 4× decoding — 4 counts per encoder line, the highest resolution you can get without extra hardware. That's what the PCNT edge/level action pattern below implements.

Why PCNT hardware, not a GPIO interrupt per edge

If you've just read about ESP-IDF GPIO interrupts, the obvious first idea is an ISR on every A/B edge that increments a counter. That works at low speed and falls apart at wheel-turning speed:

GPIO ISR per edgePCNT hardware
CPU costone interrupt per edge, forever~zero — counting happens in a hardware register
Missed edgespossible if the CPU is busy elsewhereno — hardware can't get "busy"
Debounce/glitchyou write it yourselfbuilt-in glitch filter (nanosecond-scale)

Same reason PWM uses the LEDC peripheral instead of you toggling a pin in a loop — offload anything periodic and time-critical to dedicated hardware when the chip has it.

What this chip actually has

Verified in soc/esp32s3/include/soc/soc_caps.h:

CapabilityValue
SOC_PCNT_UNITS_PER_GROUP4
SOC_PCNT_CHANNELS_PER_UNIT2

4 independent counting units, 2 channels each — exactly enough for one unit per wheel, both channels used for 4× decoding. Nothing left over for a third wheel if you ever add one, but you don't need it here.

API: use pulse_cnt.h, not pcnt.h

Most tutorials and forum posts online use the old driver. ESP-IDF ≥5.0 replaced driver/pcnt.h with the object-handle-based driver/pulse_cnt.h (pcnt_new_unit, pcnt_new_channel, pcnt_channel_set_edge_action...). They are not interchangeable — code written against the old API won't compile against this IDF version. A working reference in the current API already exists on this machine: $IDF_PATH/examples/peripherals/pcnt/rotary_encoder/.

Gotcha 1 — the counter is 16-bit and wraps

You configure a high_limit / low_limit (e.g. ±100). Once the count reaches either, it wraps back around rather than overflowing silently — but it still means pcnt_unit_get_count() alone cannot track total distance travelled, only recent motion. Fine for measuring speed (T6), not enough by itself for a running distance total — that needs a watch-point callback that increments a separate overflow counter each time a limit is hit. Keep this in mind; it's exactly what T6 builds on.

Gotcha 2 — two of your encoder pins are strapping pins

Look this up before wiring anything permanently. enAB is GPIO3 and enBA is GPIO46 in your current pin map. Both appear on Espressif's ESP32-S3 strapping-pin list — pins sampled at reset to configure boot behaviour. An encoder holding one of these high or low during power-up/reset can change how the chip boots. Find the ESP32-S3 datasheet's strapping-pin table yourself and check GPIO3 and GPIO46 against it — this is the task below, not something to take on faith.

Code skeleton

One PCNT unit per wheel. This shows the shape for motor A's unit — you write motor B's the same way, then a place to read both. Fill each n.

#include "driver/pulse_cnt.h"

#define ENC_HIGH_LIMIT 1
#define ENC_LOW_LIMIT  1

pcnt_unit_handle_t unitA = NULL;

void encoders_init(void)
{
    pcnt_unit_config_t unit_cfg = {
        .high_limit = ENC_HIGH_LIMIT,
        .low_limit  = ENC_LOW_LIMIT,
    };
    ESP_ERROR_CHECK(pcnt_new_unit(&unit_cfg, &unitA));

    pcnt_glitch_filter_config_t filter_cfg = {
        .max_glitch_ns = 2,
    };
    ESP_ERROR_CHECK(pcnt_unit_set_glitch_filter(unitA, &filter_cfg));

    pcnt_chan_config_t chanA_cfg = {
        .edge_gpio_num  = 3,
        .level_gpio_num = 3,
    };
    pcnt_channel_handle_t chanA = NULL;
    ESP_ERROR_CHECK(pcnt_new_channel(unitA, &chanA_cfg, &chanA));

    pcnt_chan_config_t chanB_cfg = {
        .edge_gpio_num  = 4,
        .level_gpio_num = 4,
    };
    pcnt_channel_handle_t chanB = NULL;
    ESP_ERROR_CHECK(pcnt_new_channel(unitA, &chanB_cfg, &chanB));

    // 4x decode: every edge on A or B counts, direction set by the other
    // channel's current level
    ESP_ERROR_CHECK(pcnt_channel_set_edge_action(chanA,
        5, 5));
    ESP_ERROR_CHECK(pcnt_channel_set_level_action(chanA,
        6, 6));

    ESP_ERROR_CHECK(pcnt_channel_set_edge_action(chanB,
        7, 7));
    ESP_ERROR_CHECK(pcnt_channel_set_level_action(chanB,
        7, 7));

    ESP_ERROR_CHECK(8);   // enable the unit
    ESP_ERROR_CHECK(8);   // clear count to 0
    ESP_ERROR_CHECK(8);   // start counting
}

// somewhere in your loop:
int count = 0;
ESP_ERROR_CHECK(9);
ESP_LOGI(TAG, "motor A ticks: %d", count);

Checkpoints

You're done when: both wheels report a tick count over serial; turning a wheel by hand one full revolution and back returns to (approximately) the same count; the sign flips correctly between the two directions; and you've confirmed GPIO3/GPIO46 either boot safely as-is or you've moved the encoder to different pins.

Common failure modes

  • Count stuck at 0. Check the unit was actually started, not just enabled — both are required. Also check the encoder's own power pins.
  • Count changes but never goes negative. Likely only counting one edge action, or A and B are swapped between the two channel configs — re-check against the state table.
  • Count is roughly half or quarter of what you expect. You're getting 1× or 2× decode instead of 4× — check both edge and level actions are set on both channels.
  • Erratic jumps at rest. Electrical noise on the line — increase the glitch filter's max_glitch_ns, and check the encoder's ground connection.
  • Board misbehaves on boot after wiring GPIO3/46. This is the strapping-pin issue — move the encoder wire to a free GPIO not on the strapping list.
