ESP-IDF Project & Flash Round-Trip

Get a real ESP-IDF project building, flashing, and logging on your board — the foundation everything else sits on.
⏱ 60–75 min
🎯 Goal: a log line ticking once/sec over serial
📍 /dev/ttyACM0

Before you start

✅ Toolchain is ready. ESP-IDF v5.3.2 (esp32s3 target) finished installing via eim install on 2026-08-09. Verified: idf.py --version prints ESP-IDF v5.3.2-dirty (the "-dirty" suffix is normal/harmless for this kind of clone).

To get an IDF-aware terminal: either use the VS Code extension's own terminal (it exports the environment automatically once you open a folder with an IDF project), or run this in any terminal first: 
source ~/.espressif/tools/activate_idf_v5.3.2.sh
Then idf.py --version should work in that shell.

Background to look up

  • ESP-IDF "Hello World" / getting started — Espressif's own walkthrough of what idf.py does and the shape of a minimal project. docs.espressif.com → Get Started (ESP32-S3)
  • Build system — how a project's top-level CMakeLists.txt differs from a component's CMakeLists.txt (e.g. the one inside main/). docs.espressif.com → Build System
  • Logging — ESP_LOGI/ESP_LOGW/ESP_LOGE vs plain printf: what a log tag is, why the IDF logging macros are generally preferred in FreeRTOS-based firmware. docs.espressif.com → Logging library
  • Delays in a FreeRTOS task — what vTaskDelay and pdMS_TO_TICKS actually do (this matters again in T7, so understand it now, not just copy it).
  • VS Code Espressif extension — the "ESP-IDF: New Project" command, and separately what "ESP-IDF: Set Espressif Device Target" does.

Tasks

  1. Create the project. Command Palette (Ctrl+Shift+P) → "ESP-IDF: New Project". Point it at ~/robot_learner/firmware. Note what target/board options it shows you and pick the one for the S3. If it offers a template, pick the plainest one (e.g. template-app or hello_world).
  2. Read before you edit. Open the generated top-level CMakeLists.txt and main/CMakeLists.txt side by side. Write down, in your own words, what each one is responsible for.
  3. Confirm the target. In a terminal in the project folder, run idf.py set-target esp32s3. Watch what it prints and what changes on disk afterward (hint: look at what appears or changes in the project root).
  4. Modify main/main.c (or .cpp) so it logs a message once per second, forever, using ESP_LOGI with a tag of your choosing — not printf. Include something that changes each time (e.g. a counter) so you can tell it's actually looping and not stuck.
  5. Build. idf.py build. Read any errors fully before asking for help — the first error in the log is usually the real one; the rest are often noise from it.
  6. Flash and monitor. idf.py -p /dev/ttyACM0 flash monitor. Confirm you see your ticking log line. Leave it running for at least 15–20 seconds — a message that only prints once is a different bug than one that never appears.
  7. Exit cleanly. Find and use the keybinding to exit idf.py monitor without killing your terminal (it's in the banner IDF prints when monitor starts).

Checkpoints

You're done when: idf.py build exits with no errors, idf.py -p /dev/ttyACM0 flash monitor flashes successfully, and you see a log line incrementing once per second in the monitor output, and you can exit monitor without closing the terminal.

Common failure modes

  • "Permission denied" opening /dev/ttyACM0. Already fixed for this board/user (dialout group + cdc_acm blacklist removed) — if it recurs after a reboot, check groups includes dialout and ls -la /dev/ttyACM0.
  • Board doesn't enter flashing mode. Some S3 clones need BOOT held while tapping RESET for the first flash. If idf.py flash hangs at "Connecting...", try that before assuming a wiring/firmware problem.
  • Wrong or stale target. If you copy-pasted a project or reused sdkconfig from elsewhere, idf.py set-target may silently not be esp32s3. Re-run it explicitly if the build errors mention a different chip.
  • idf.py: command not found. Means the IDF environment isn't exported in that terminal (or the install isn't finished). The VS Code extension's own terminal usually exports it automatically — prefer that over an arbitrary shell while you're still confirming the install.
